# 智能推荐算法重构 Design

**Date:** 2026-05-20

## Goal

把当前“所有内容混合后一次性打分排序”的推荐流程，重构成更稳定的“两阶段推荐”：先分池召回，再统一重排。重点先解决推荐页同来源刷屏问题，同时顺带改善推荐不准、热搜权重过高、已读/不喜欢内容仍靠前等体验问题。

## Current Problems

### 1. 单阶段排序把多个目标糊在一起

当前 `public/app.js` 里的 `buildHybridFeed()` 同时负责：
- 合并 RSS 与热搜
- 计算兴趣/历史/时间/热度分
- 做少量类型多样性补偿
- 直接返回最终排序

这导致相关性、多样性、新鲜度、来源分布几个目标互相打架，调一个参数很容易把另一个方向带坏。

### 2. 来源刷屏控制太弱

当前只有“top 8 至少保留一定 rss/hot 比例”的轻量补偿，没有平台/来源连续出现控制。所以当微博、头条、某几个 RSS 源分数高时，很容易连续霸榜。

### 3. 热度与随机扰动容易压过用户偏好

热搜内容基础热度高，加上当前存在较大随机抖动，前排结果更像“随机热榜混排”，不够像“围绕用户兴趣的推荐”。

### 4. 已读/不喜欢信号不够强

已读内容只进入历史关键词权重，没有直接的前排惩罚；不喜欢词有惩罚，但仍在单阶段排序里被热度、新鲜度抵消。

## Design

### Architecture

推荐链路改成两阶段：

1. **召回阶段**
   - 从现有 RSS 与热搜内容中拆出多个候选池
   - 每个池子只解决“找哪些候选”问题，不负责最终排序

2. **重排阶段**
   - 统一比较候选项
   - 综合相关性、新鲜度、热度、来源多样性、主题多样性、已读/不喜欢惩罚
   - 前排加来源配额与相邻去重，解决刷屏问题

后端接口、状态结构、推荐页渲染入口不变。只重构推荐构建逻辑，尽量把改动收敛在 `public/app.js` 推荐相关区域。

### Candidate Pools

候选池分成 4 类：

- **兴趣池**
  - 命中兴趣标签关键词，或命中历史行为高频关键词
  - 这是主池，负责“推荐要像用户想看”

- **新鲜池**
  - 未必强相关，但发布时间新
  - 负责避免旧内容重复回流

- **热点池**
  - 来自热搜内容，保留全网热点感知
  - 负责“你可能也该知道”

- **探索池**
  - 不强依赖兴趣和历史，少量补充长尾内容
  - 负责避免推荐越看越窄

### Pool Mix Strategy

建议默认配额：

- 兴趣池：50%
- 新鲜池：20%
- 热点池：20%
- 探索池：10%

配额作用在“候选集构建”阶段，不是死板最终展示比例。若某池候选不足，空位按优先级回流到兴趣池、新鲜池。

### Scoring Model

每条内容拆分计分，避免单一分项统治结果：

- **兴趣分**
  - 命中用户显式兴趣标签，加较高分

- **行为分**
  - 命中浏览历史高频关键词，加中等分
  - 高频关键词加成设上限，避免单个词把列表彻底带偏

- **时间分**
  - 24 小时内加成最高
  - 24～72 小时逐步衰减
  - 超过 72 小时明显降权

- **热度分**
  - 只对热搜类内容生效
  - 保留热点价值，但权重低于“强兴趣命中”

- **惩罚分**
  - 命中不喜欢关键词：强惩罚
  - 已读内容：强降权，避免反复回前排
  - 同主题连续出现：逐步惩罚
  - 同来源连续出现：逐步惩罚

### Diversity Reranking

最终重排阶段加 3 个约束：

1. **来源配额**
   - 前 10 条里，同来源最多 3 条
   - 对热搜来源和 RSS 源统一处理

2. **相邻去重**
   - 相邻两条尽量不来自同来源
   - 若候选不足，再允许回退

3. **主题衰减**
   - 如果前几条已经连续命中同主题关键词，后续同类项逐步降权
   - 不追求精准聚类，只做轻量关键词簇衰减

### Read / Dislike Handling

- `recordView()` 继续保留现有历史记录逻辑
- 新增“已读标题/URL 惩罚”参与排序，而不只是给历史关键词加权
- `addDislike()` 保留现有关键词抽取方式，但在重排阶段提升其惩罚优先级

目标不是完全隐藏内容，而是把已读/不喜欢内容从前排明显压下去。

## File Changes

### `public/app.js`

建议把当前 `buildHybridFeed()` 附近逻辑拆成以下几个职责清楚的函数：

- `buildCandidatePools()`
  - 输入：`state.articles`, `state.hotItems`
  - 输出：兴趣池 / 新鲜池 / 热点池 / 探索池

- `scoreCandidate(item, context)`
  - 单条打分
  - 返回拆分后的分值明细与总分

- `mergeCandidatePools(pools)`
  - 按配额合成候选集

- `rerankCandidates(items)`
  - 做来源配额、相邻去重、主题衰减、已读/不喜欢惩罚

- `buildHybridFeed()`
  - 退化成编排入口：组装上下文 → 召回 → 合并 → 重排 → 返回结果

这次不拆新文件，先留在 `public/app.js`。原因：当前项目推荐逻辑尚小，先把职责分开，比立即跨文件拆分更稳。

## Testing Strategy

先补推荐逻辑专项测试，再改实现。测试重点：

1. 来源配额
   - 前 10 条里单来源不超过 3 条

2. 相邻去重
   - 候选足够时，相邻两条不出现同来源

3. 热点不过载
   - 高热度内容不能在无兴趣优势时压过强相关 RSS

4. 已读降权
   - 已读内容不再稳定留在前排

5. 不喜欢惩罚
   - 命中不喜欢关键词内容明显后移

6. 候选池回流
   - 某池候选不足时，结果仍能补足列表长度

建议新增单测文件，直接测纯函数，不依赖 DOM。

## Success Criteria

实现后，推荐页应满足：

1. 前 10 条不再被单一来源刷屏
2. 相邻卡片大多不是同来源
3. 热榜仍存在，但不再压住高相关 RSS
4. 已读/不喜欢内容明显减少前排出现
5. 推荐结果比当前更分散，但仍保持相关性

## Non-Goals

这次不做：

- 后端模型或向量召回
- 实时在线学习
- 复杂埋点与停留时长优化
- 多文件大拆分或新状态系统

先把当前前端本地推荐逻辑重构到“更像推荐系统”，再决定要不要继续升级。
