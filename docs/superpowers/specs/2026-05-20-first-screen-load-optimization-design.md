# 首屏加载优化设计

> 目标：减少首屏白屏等待时间，让页面框架与基础内容更快出现，同时保持现有接口与功能不变。

## 背景

当前首屏初始化集中在 `public/app.js` 的 `init()` 中，使用 `await Promise.all([loadSources(), loadArticles(200), loadHotData(), loadStats()])` 后才调用 `renderTab()`。这意味着页面必须等待多个请求全部完成后才能渲染。

现状中，`/api/articles?limit=200` 与 `/api/hot/trending` 返回体较大，是首屏阻塞的主要来源。即使某些数据已经可用，用户也要等所有数据齐备后才能看到界面，造成“打开页面后首屏出来慢”的体感。

## 目标

- 页面结构和基础 UI 尽快出现，减少首屏白屏时间
- 将首屏首次文章加载量从 200 降到较小数量，降低首包体积
- 数据按模块异步补齐，不再让热搜、文章、统计彼此阻塞
- 不改后端接口，不改数据库结构，不改现有功能语义

## 非目标

- 不新增后端轻量接口
- 不重写推荐算法或 feed 分页机制
- 不引入复杂的 skeleton 组件体系
- 不改动热搜抓取与 RSS 抓取逻辑

## 方案

### 1. 初始化改成“先渲染，再补数据”

`init()` 调整为：
1. 恢复本地状态与主题
2. 立即渲染当前 tab 框架
3. 并发请求 `sources / hot / stats / articles`
4. 哪个数据先回来，就更新对应 state，并在当前 tab 需要时局部重渲

这样用户先看到页面结构，再看到内容逐步补齐。

### 2. 推荐页首次文章量下调

首屏不再请求 `loadArticles(200)`，改成较小数量，建议 `30`。这能直接减少 `/api/articles` 首包大小，降低推荐页首屏等待。

后续仍保留现有 feed 分页与刷新逻辑，不扩展新机制。

### 3. 推荐页允许分块出现

推荐页中：
- 热榜摘要卡片在 `hotItems` 返回后再出现
- feed 列表在文章返回后再出现
- 状态、来源信息不阻塞 tab 初次显示

这要求 `renderRecommendTab()` 在数据为空时能稳定渲染容器与轻量占位，而不是依赖所有数据先就绪。

## 数据流调整

- `state.articles`、`state.hotItems`、`state.sources`、`state.stats` 初始为空
- 首次 `renderTab()` 基于空 state 渲染基础结构
- 异步加载函数完成后，更新对应 state
- 若当前 tab 依赖该数据，则再次调用 `renderTab()` 或局部刷新

## 风险与取舍

- 首屏“完整内容完全加载”的总时长未必显著下降，但可见速度会明显提升
- 由于先渲染空态，若占位文案处理不好，可能出现短暂“空白模块”感受
- 多次局部重渲需要避免重置用户交互状态，因此只在当前 tab 相关数据变化时刷新

## 验证标准

- 打开页面后，tab 与主要布局应快速出现，不再等待所有请求完成
- 推荐页首次请求文章数明显下降
- 热榜摘要与推荐 feed 可异步补齐
- 热榜页、RSS 页、刷新按钮、推荐页交互不回退

## 实施建议

优先做最小实现：
1. 修改 `init()` 初始化顺序
2. 将首屏文章数从 200 降到 30
3. 调整推荐页空数据时的渲染行为
4. 回归验证首屏、切 tab、刷新
