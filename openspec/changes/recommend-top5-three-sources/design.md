## Context

当前智能推荐页的“实时热榜 Top 5”摘要卡片在 `public/app.js` 中直接对 `state.hotItems` 执行 `slice(0, 5)`。由于 `state.hotItems` 包含多个平台的混合热榜数据，摘要卡片会展示来自不同平台的前 5 条内容，其中可能包含热度相对较低的平台，和用户希望突出头条、百度、微博三个高热来源的预期不一致。

这个变更只涉及前端展示层规则调整。热榜数据仍由现有 `/api/hot/trending` 接口统一返回，热榜 Tab 仍需要保留全平台视图，因此不适合在接口层裁剪数据。

## Goals / Non-Goals

**Goals:**
- 让智能推荐页摘要卡片只展示头条、百度、微博三个平台的数据
- 保持现有接口、数据结构、卡片样式和点击行为不变
- 将变更控制在最小范围，不影响热榜 Tab 与推荐流其他逻辑

**Non-Goals:**
- 不调整 `/api/hot/trending` 接口返回内容
- 不改动热榜 Tab 的全平台展示规则
- 不引入按平台均衡分配、二次排序或热度重算逻辑
- 不修改推荐算法或用户兴趣打分逻辑

## Decisions

### 决策 1：在 `renderDailyDigest()` 中本地过滤三源后再取前 5
- 方案：对 `state.hotItems` 先过滤出 `platform` 属于 `toutiao`、`baidu`、`weibo` 的项目，再 `slice(0, 5)`。
- 原因：摘要卡片是展示层需求，直接在渲染函数中约束来源，改动最小，且不会影响其他消费 `state.hotItems` 的逻辑。
- 备选方案：在 `loadHotData()` 阶段裁剪全局状态。未采用，因为这样会连带影响热榜 Tab 等全平台视图。

### 决策 2：三源不足 5 条时不使用其他平台补位
- 方案：严格展示三源实际可用条数。
- 原因：用户已明确要求“固定三源”，补位会重新引入低优先级平台，违反需求。
- 备选方案：不足 5 条时回退其他平台补齐。未采用，因为会削弱约束的一致性。

### 决策 3：保留现有卡片结构与文案
- 方案：卡片标题仍为“实时热榜 Top 5”，现有 badge、点击跳转、排序样式保持不变。
- 原因：本次需求只调整数据来源，不涉及 UI 重构，避免扩大范围。

## Risks / Trade-offs

- [三源数据总量不足，卡片可能少于 5 条] → 接受该结果，保持需求一致性，不使用其他平台补位
- [接口返回的平台字段异常导致部分条目被过滤] → 依赖现有平台标识约定，仅筛选已知的 `toutiao`、`baidu`、`weibo`
- [“Top 5” 文案与实际少于 5 条存在轻微语义偏差] → 先保持现有文案不变，避免额外 UI 变更
